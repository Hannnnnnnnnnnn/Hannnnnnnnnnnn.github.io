## 1. 지난 로그의 "원인 미확인"이 닫혔다 — 범인은 `place-items` 였다

지난 세션은 이렇게 적고 끝냈다: figcaption 이 736px 부모 안에서 614px 로 줄어드는데,
매칭되는 5개 규칙 중 width 를 거는 것이 없어 **원인을 못 찾았다.** 그래서 `width: 100%` 를
명시하고 "미확인"이라고 남겼다.

원인은 `place-items` 였다.

`figure.figure--diagram` 은 `.figure` 의 `display: grid` 를 `block` 으로 되돌리는데,
**`place-items: center` 는 같이 안 지워진다.** 그리고 `justify-items` 는 블록 레이아웃의
자식에게도 적용된다 — 자식이 `justify-self: center` 가 되면서 `width: auto` 가
shrink-to-fit 으로 바뀐다. 그래서 736px 부모 안에서 `.dist` 가 137px 로, figcaption 이
614px 로 줄었다. `place-items: normal` 을 padding 과 같은 요소+클래스 선택자에 얹어 해결.

**함정 18("무엇이 이기고 있는지 뽑아 봐라")의 미해결 사례가 하나 닫혔다.** 다만 그때
매칭 규칙을 전부 뽑고도 못 찾은 이유가 남는다 — **뽑은 것이 그 요소에 매칭되는 규칙뿐이었고,
부모에서 상속·잔존하는 값은 목록에 없었다.** `el.matches(selector)` 스윕은 "이 요소를
누가 이기는가"는 잡지만 "부모가 무엇을 남겨놨는가"는 못 잡는다. 폭이 이상하면
`getComputedStyle(parent)` 도 같이 봐라.

**남은 빚:** 이제 `.figure--diagram figcaption { width: 100% }` 는 아마 불필요하고, 바로
위 주석은 여전히 "원인을 확정하지 못했다"고 말한다. 새로 넣은 `place-items` 주석과 정면으로
모순된다. 지우기 전에 실제로 재봐야 해서 이번엔 손대지 않았다.

## 2. 이번 세션의 시간은 전부 "측정 장치를 안 의심한 것"에 들어갔다

카운터의 카운트업을 붙이고 자동화 탭에서 검증했다. 값이 `124,866` 에서 꿈쩍도 안 했다.
여기서 **코드가 안 도는 이유를 찾기 시작한 게 잘못이었다.**

순서대로 확인한 것들: `reduce` 플래그(false), 요소 존재(있음), `IntersectionObserver`
지원(됨), 서버가 주는 `main.js` 에 블록이 들어있는지(들어있음), `run()` 블록 경계가
깨졌는지(멀쩡함), 콘솔 에러(없음). 전부 정상인데 안 돈다.

그 다음에야 블록의 로직을 손으로 그대로 실행해 봤다. `el.textContent = fmt(0)` 까지는
반영되는데 **rAF 틱이 한 번도 안 왔다.** 그제서야 `document.visibilityState` 를 찍었다 —
`"hidden"`.

같은 세션에서 같은 증상을 만든 원인이 **세 개**였다.

| 증상 | 실제 원인 | 이미 적혀 있던 곳 |
|---|---|---|
| 카운터가 안 셈 | 숨은 탭이라 rAF·IO 정지 | 함정 4, 함정 3 |
| `scrollIntoView` 후에도 요소가 6522px 밖 | `scroll-behavior: smooth` 라 도착 전에 측정 | 함정 3 |
| 320px 검증이 500px 로 나옴 | 자동화 창 크기 변경이 500px 아래로 안 내려감 | 함정 8 |

**셋 다 `CLAUDE.md` 검증 섹션에 이미 있다.** 3번은 문장까지 그대로다 — "숨겨진 자동화
탭에서는 IntersectionObserver 가 아예 발화하지 않는다… 스크롤 → 스크린샷 → 상태 읽기
순서로 해라." 나는 그 순서를 안 지키고 JS 로만 찔러 보고 있었다.

결국 `computer` 의 실제 스크롤 액션(스크린샷을 동반해 프레임을 강제한다)으로 바꾸자
한 번에 세는 게 보였고, `124,866` 에 안착하는 것까지 확인했다.

**교훈: 모션·관찰자·좁은 폭을 자동화 탭에서 검증할 때는 코드를 의심하기 전에
`visibilityState` · `scroll-behavior` · 실제 뷰포트 폭 세 개를 먼저 찍어라.**
그리고 더 값싼 교훈 하나 — **이 파일의 검증 섹션을 세션 시작할 때 읽어라.** 이번에 든
비용은 전부 이미 지불된 적 있는 비용이었다.

## 3. "오버플로 없음"이 "잘 읽힌다"는 뜻은 아니다

320px 에서 카운터를 검사했더니 `scrollWidth > clientWidth` 가 false 로 나왔다. 통과시킬
뻔했다. 실제로는 숫자와 단위가 한 줄에 못 들어가서 **`"bottles upcycled"` 만 두 줄로
쪼개져 숫자 옆에 걸쳐** 있었다.

flex item 은 기본 `flex-shrink: 1` 이라 폭이 모자라면 **넘치지 않고 안의 텍스트를 줄바꿈한다.**
그래서 오버플로 검사는 조용히 통과한다. `flex-wrap: wrap` 을 주면 항목 단위로 넘어가
숫자 한 줄 · 단위 한 줄로 가운데 정렬되고, 끊기는 자리가 문구 그대로 남는다.

**오버플로 검사는 "깨졌는가"만 잡고 "읽히는가"는 못 잡는다.** 좁은 폭에서는 줄이 어디서
끊기는지를 직접 봐야 한다. → 함정 22 로 추가.

## 4. 라이브를 재다가 케이스의 주장과 어긋나는 값이 나왔다

카운터 값을 재려고 라이브 블록의 data 속성을 읽었는데:

    data-starting-number  = 103482
    data-pet-bottle-total = 21384.0
    data-current          = 124866.0      (= 103482 + 21384)

**124,866 중 103,482(83%)가 하드코딩된 상수다.** 주문에서 파생되는 것은 21,384 뿐이다.

그런데 02 케이스의 `.mfd__note` 는 이렇게 말한다 — *"The total is derived, not stored:
it is read from orders across all channels and summed."* 본문도 "nobody updates that
number… it goes up whether or not anyone remembers to maintain it."

103,482 가 **쇼피파이 이전 시기의 실제 누적 생산량**이라면 "축적된 사실"이라는 주장 자체는
참이고 "전부 주문에서 파생된다"는 서술만 틀린 것이다. 그 숫자의 출처를 알 수 없어서
소유자에게 넘겼고 문구는 건드리지 않았다. **미결.**

## 5. 라이브와 일부러 다르게 한 두 가지 (둘 다 주석에 남김)

1. **`font-variant-numeric: tabular-nums`.** 라이브는 이걸 안 걸어서 세는 동안 숫자가
   미세하게 떨린다. 이 띠가 라이브보다 작아 떨림이 더 눈에 띄므로, 편차보다 떨림이 나쁘다고
   보고 걸었다.
2. **`flex-wrap: wrap`.** 3번의 이유.

나머지는 전부 실측값이다: Poppins, 숫자 20px/700 `#f15a29`, 단위 20px/600 `#0c0c0c`,
사이 6px 베이스라인 정렬, 숫자 아래 12px, 설명 12px/16.8px, 컨테이너 400px, 흰 바탕.
무대가 tint 라 흰 배경은 띠가 직접 들고 있다.

카운트업은 **이미 맞는 숫자 위에 얹는 것**이라, JS 가 없거나 모션 최소화면 `124,866` 이
그대로 보인다. 2번 리빌과 달리 IO 하나로 충분한 이유도 그것이다 — 리빌은 콘텐츠를 숨겨
두고 IO 로 되돌리는 구조라 콜백이 없으면 영영 안 보이지만, 이쪽은 콜백이 없으면
애니메이션만 없다.
